# 系列 / 角色项目

## 适用

- 同一角色或同一世界观要出多张图：设定图、三视图、多个场景、多种状态。
- 核心矛盾：每张图单独写提示词，角色就会漂移。所以先把“不变的部分”固化下来，再逐张写“变化的部分”。
- 不适用：只要一张图，走 `flows/single-image.md`；要在几个设计方向中挑一个，走 `flows/explore-variants.md`。

## 阶段总览

```text
① 第一性问题 ─▶ ② 建项目目录 ─▶ ③ 写固定设定文件 ─▶ ④ 样张锁画风
      ─▶ ⑤ 设定图（三视图 + 细节格 + 状态格）─▶ ⑥ 场景卡 ─▶ ⑦ 批量生成 ─▶ ⑧ 统一验收 ─▶ ⑨ 定稿归档
                 ▲                                         │
                 └──── 用户否决设计时回到 ③ 改设定，不在场景提示词里打补丁 ────┘
```

进入每个阶段时回复：“走 系列·阶段 N，依据：…；决策模式：<询问/自主/混合>；下一步 …”。

## ① 第一性问题（需求抽象时必问）

用户一开始的描述往往是几个形容词。第一版被否之后，不要靠猜调整，先问清下面几件事：

1. 用途：头像、品牌拟人、游戏角色、插画系列？决定华丽程度，以及一致性要求有多高。
2. 气质：用户给的几个形容词，哪几个必须同时成立、哪个最重要。
3. 世界观：时代、地域、幻想程度，决定服装和场景语言。
4. 年龄感与体型：避免画出儿童感或学生感（成年角色要明确写成年）。
5. 画风目标：用户心里的参照，写实还是二次元、精致还是粗犷。具体定档在第 ③ 步读维度卡时完成。

自主模式下：根据已有描述推断这五项，写进 `notes.md` 并标“推断”；交付样张时请用户确认或推翻。

## ② 建项目目录

```text
<项目>/
├─ notes.md           # 只追加：需求原话、用户决定、否决和理由、提示词教训
├─ 设定.md            # 定稿后的角色设定（中文，给人看）
├─ prompts/
│  ├─ _spec.txt       # 固定设定文件（英文，给模型看）
│  └─ NN-<名称>.txt   # 每张图的规格，编号表示阶段：0x 设定，1x–2x 探索，5x 场景，6x 修图
├─ ref/               # 用户参考图，以及裁好的局部
├─ output/            # 全部生成产物，按版本号保存
└─ 成品/              # 用户确认后的定稿副本
```

## ③ 写固定设定文件 `prompts/_spec.txt`

写之前读取 `catalog/README.md`，按“系列项目写固定设定时”一行选卡（全部 7 张）。

结构（英文）：

```text
Use case: <slug>
Style/medium: <写实刻度锚定词，一句话说清是什么渲染>
Rendering rules:
- Skin: ...
- Face: <脸型结构；眼睛按形状、眼睑、虹膜、视线逐项描述>
- Hair: ...
- Clothing / materials: ...
- Lighting: ...
Character (original design, keep identical in every image): <年龄、体型、头身比、气质；明确 young adult、never childlike 等>
- Hair: ...
- Signature accessory: <精确形状、计数、位置、尺寸、状态规则>
- Outfit: <从上到下逐件写：轮廓、材质、颜色、细节、计数>
- Forbidden on the outfit: <不许出现的东西，例如 nothing hangs from the waist>
States: <若有状态系统：每种状态下表情、配饰亮灭的规则>
Anatomy and physics (strict): <五指、关节、肢体等长、接触阴影、只有光可以悬浮>
Avoid: <画风上的相邻档、已知漂移（颜色、形状）、版权元素>
```

规则：

- 固定设定只维护这一份。每张场景图都用 `--spec prompts/_spec.txt` 拼接，场景文件里不重复描述角色外观。
- 用户否决某个设计时，改 `_spec.txt` 后重出受影响的图，不在单个场景文件里写“这次衣服改成……”。
- 每个容易漂移的点（颜色、计数、形状）都要写正向描述，再加排除。例如丝袜写“中性冷黑，不发棕”。
- 有状态系统的（表情、配饰发光、伙伴是否出现），用一张状态表写清规则，场景里只写 `State: <名称>` 和这张图的具体表现。

## ④ 样张锁画风

- 先出一张展示图：全身、三分之四侧面、机位在胸口高度、长焦无畸变、简洁舞台背景。
- 只用它确认画风和整体比例。用户点头前，不出设定图和场景。
- 画风被否时，回到写实刻度卡重新定档，改 `_spec.txt` 的 Style 和 Rendering 段。

## ⑤ 设定图

- 一张横幅设定图：左侧放三视图（正面、侧面、背面，同一比例、同一地平线），右侧放细节格（配饰亮灭对比、鞋、领口、动态布料）和状态格（各状态的头肩像）。
- 提示词写明：
  - 整体版式：左侧占多少、右侧几行几格。
  - 每一格画什么、不画什么，例如“这一格只有裙摆，不出现手”。
  - No labels, no text, no arrows。
- 参考图：用定稿的样张做 Image 1，配饰定稿图依次往后排，每张都写清职责。

## ⑥ 场景卡

写场景卡前读取 `catalog/README.md`，按“系列项目写场景卡”一行选卡。

每个场景先写一张卡，覆盖不同姿态、角度、景别和互动物：

| 编号 | 场景 | 比例 | 镜头 | 动作与互动物 | 状态 |
|---|---|---|---|---|---|

- 人和道具有接触的，必须在同一张图里生成，不靠后期拼贴。
- 每个场景的提示词模板：

```text
Asset type: finished in-game cinematic scene, <比例>.
Input images: Image 1 is the approved character reference sheet and Image 2 the approved full-body look. Match her face, hair, outfit, accessories and rendering exactly. Do not reproduce their layout, pose or background.
State: <状态名>. <配饰亮灭、伙伴是否出现>
World: <世界观一句话>
Scene: <环境；结构性物体写清结构与透视，例如梯子横档平行、窗框透视一致>
Framing: <景别、机位高度、角度、焦段；不雅角度排除>
Pose and interaction: <逐部位；握法；接触点>
Expression: <程度 + 排除>
Lighting: <光源与落点；接触阴影>
```

## ⑦ 批量生成

- 每张图调用一次：

```text
python <skill目录>/scripts/gen.py --prompt prompts/<NN-名称>.txt --spec prompts/_spec.txt --out-dir output --name <NN-名称> --ref <设定图> --ref <全身图>
```

- 修图类提示词（编辑模式）不要拼固定设定，去掉 `--spec`，改用 `flows/edit-refine.md` 的模板。
- 可以并行，但每张都按单张额度计费。中途取消时，要确认 codex 子进程已经结束。
- `gen.py` 依赖本机已登录的 Codex CLI，以及 Python 3.10+ 标准库。判断成败只看脚本是否打印“完成”以及输出文件是否存在。终端里的 PowerShell profile 报错和生图无关。

## ⑧ 统一验收

在 `notes.md` 里维护一份项目级验收清单，每张图都按它检查：

- 人体：五指、指节方向、握持有接触、四肢等长、脚踩实地面、成年比例。
- 造型一致性：签名配饰的计数和位置（放大核对）、颜色是否漂移、禁止项是否出现。
- 状态：表情、配饰亮灭是否符合状态表。
- 物理结构：家具腿数和落地、梯子和窗框的结构与透视、物体不悬空不穿插、倒影对应。
- 画面：没有可读文字、乱码或水印；构图端庄。

单张需要修复时，转 `flows/edit-refine.md` 执行，修完回到本流程继续。

## ⑨ 定稿归档

- 用户确认的版本复制到 `成品/`，文件名以场景编号开头。
- `设定.md` 同步定稿内容，包括外观、配饰、状态表和场景表。
- `notes.md` 追加本项目的提示词教训。能通用的，再按 `flows/maintain.md` 回写到本 skill。

## 决策点

| 决策点 | 选项 | 自主默认 | 即使在自主模式也要问 |
|---|---|---|---|
| 第一性五问 | 问用户 / 推断 | 推断并标“推断”，交付样张时请用户确认 | 用途完全不明，例如不知道是头像还是游戏角色 |
| 写实刻度 | 维度卡里的 6 档 | 按用户用词就近定档 | 用户用词同时指向两档 |
| 是否建状态系统 | 建 / 不建 | 用户提到情绪变化、配饰发光、伙伴时才建 | — |
| 样张确认 | 等用户确认 / 直接继续 | 停下来等确认（画风错了，后面全部白做） | 始终要问 |
| 场景数量与清单 | 场景卡表 | 先列场景卡给用户看 | 一次要生成超过 3 张（额度闸门） |
| 用户否决设计时 | 改设定 / 改单张 | 改 `_spec.txt` 后重出受影响的图 | 受影响的图超过 3 张 |

## 交付口径

- 每阶段结束时给出产物路径、对照表，以及需要用户拍板的点（画风、设计取舍）。
- 被否的方案和理由记进 `notes.md`，下一轮设计必须回应这些理由。
- 自主或混合模式下，列出《我替你做的决定》：决定、理由、怎么推翻。
- 列出《可选方向》：例如补哪些场景、哪些设计还可以再探索。
